Executive Visibility Review & Recommendations

Scope 4tExecutive · 4thealth+ · 4tlog Lens Director of Infrastructure & Networking, daily driver Date 2026-08-27

4tExecutive now has motion — charts, time ranges, a real visual identity. This review asks a harder question: does the page answer what a director actually walks in asking? Three findings shaped everything below.

The best data never reaches the dashboard

4thealth+ already runs a 26-check device review, 7-check rule hygiene analysis, and PSIRT vulnerability matching. None of it is in the executive API.

The 4tlog contract is fiction

No summary API, no token auth, no database. faz_health and log_volume_trend are aspirational, while the FAZ APIs that would answer "who isn't logging?" sit unused.

Some tiles actively mislead

firewall_managed_count is an alias of firewalls_total; the backup tile covers the app's own files, not device configs; rule counts are up to 24 h stale.

1 · How the current page reads from the director's chair

Current widgets: hygiene score, version compliance %, pending config diffs, last backup status, firewalls online / managed, total rules, ADOM count, FortiOS version breakdown, AI usage, host CPU/memory/disk, plus the two 4tlog placeholders.

Numbers without judgment

Every widget is a value with no target, threshold, or state. A hygiene score of 71 renders identically to 94. The director's first question — is anything wrong? — requires reading every widget and knowing the targets by heart. Nothing on the page is ever red.

The richest posture data in the suite is invisible

The device review engine (HA sync, weak VPN crypto, admin MFA, trusted hosts, default admin, SNMP, logging config…), the rule hygiene engine (shadowed, unhit, unlogged, expired, disabled rules; unused objects), and the PSIRT assessment are exactly the "how exposed are we?" answers a director is asked for — and the product already computes all of them.

Redundant and misleading tiles

firewall_managed_count duplicates firewalls_total — two widgets, one number. last_backup_status reports 4thealth+'s own config-file backups, but reads as "our firewall configs are backed up." Host CPU/memory/disk of the dashboard host is ops plumbing, not executive signal.

The 4tlog side of the story doesn't exist

The contract 4tExecutive documents is unimplemented. Meanwhile 4tlog vendors the FortiAnalyzer specs (logview/logstats, eventmgmt) that would answer the highest-value logging question a director has: which firewalls are not sending logs right now? A silent device is a blind spot during an incident.

Data trust gaps under the hood

One shared status and last_updated cover fields whose real freshness ranges from live to 24 hours; a hygiene-sweep error masks a healthy device sweep. Caches are in-memory and per-worker, so consecutive polls can disagree and a restart blanks the API. A product sold on "one pane of truth" needs the pane to be honest about staleness.

2 · Recommendations

Tier 1

Presentation only — 4tExecutive changes, data already flowing

Biggest perceived-value-per-effort in this document. One release.

#RecommendationDetail
1.1Threshold-driven RAG states on every widgetConfigurable green/amber/red thresholds per widget type, with sane defaults (version compliance ≥95 green, ≥85 amber). Colored border or status dot per card. This one change converts the page from a report into a monitor.
1.2A posture strip at the topOne row above the range selector: overall state (worst-of RAG), count of widgets in amber/red, data-freshness indicator. The director's five-second answer.
1.3Merge availability into one widgetReplace Firewalls Online + Firewalls Managed with a single Fleet Availability widget: online / total (percent), charting the percentage. Drop the alias field.
1.4Relabel or demote the backup widgetRename to "App Config Backup" until real device-backup data exists (3.4), or pull it off the default layout. Never imply fleet backups are covered when they aren't measured.
1.5Move host CPU/memory/disk to AdminKeep collecting; stop spending default-dashboard real estate on the dashboard's own container.
1.6Delta annotations on charts"▲ +3 vs. start of range" beside the current value. Trend direction is the executive's unit of change.

Tier 3

New collectors and larger builds

Roadmap items — each one adds data no system collects today.

#RecommendationSystemDetail
3.1Implement the 4tlog external summary API4tlogBearer-token /external/api/executive/summary matching the 4thealth+ pattern. Minimum payload from the existing health cache: targets total/healthy, numeric FAZ disk %. Unblocks the two widgets 4tExecutive already ships.

3.5Certificate expiry4thealth+Admin/SSL certs per device; expiring-30d and expired counts. Certificate surprises are a classic director embarrassment; cheap to collect from the API already in use.
3.6License / support contract expiry4thealth+FortiCare/FortiGuard contract data via FMG; contracts expiring within 90 days. The one widget that talks to procurement.
3.7Composite Security Posture ScorebothWeighted composite of hygiene, device-review pass rate, PSIRT exposure, version compliance — weights visible and configurable. Build only after 2.1–2.3 exist; a composite over missing inputs is theater.
3.8Cache persistence & consistency4thealth+Back the executive-summary caches with SQLite (or pin sweeps to one worker) so restarts don't blank the API and multi-worker deployments answer consistently. A product requirement more than a feature.

3 · Suggested build order

  1. Tier 1 complete (one 4tExecutive release) — RAG thresholds, posture strip, widget cleanup. Biggest perceived value per effort.
  2. 2.1 + 2.3 — device review rollup and PSIRT exposure turn on the posture story with data that already exists.
  3. 3.1 + 3.2 — the 4tlog API plus silent-device detection brings the third system into the pane and adds the standout differentiator.
  4. 2.2, 2.4–2.7 as a hardening and depth wave.
  5. 3.4–3.8 as roadmap items, the composite score (3.7) last.

4 · Contract discipline — applies to every tier

  • Every new field lands in docs/integrations.md with type, null semantics, and freshness. The existing "missing key ⇒ No data yet" convention holds up well — keep it.
  • Version the executive payload (a schema_version field) before third parties integrate.
  • 4tExecutive never crashes on a malformed field — the recent null and non-numeric guards set the right precedent; extend that stance to every new field.
Bottom line: the suite already computes a director-grade posture story — device review, rule hygiene, PSIRT. The gap is almost entirely exposure and judgment (thresholds), not collection. Tier 1 plus two Tier 2 items delivers most of the executive value in this document.
